## 一、项目摘要

MEELO 咪楼是一款基于 Three.js 的三维时间记录与生活规划原型。项目把日常活动转换为可以不断生长的微缩建筑：一项活动对应一个房间，一段时间形成一个楼层，一天的生活逐渐成为一栋属于自己的楼。

与以数字、列表和完成率为中心的工具相比，MEELO 尝试提供另一种理解时间的方式。工作可以是一间书房，吃饭可以是一间温暖的厨房，睡觉也可以是一层值得被记录的生活。小猫则作为用户在建筑中的化身，让记录从一次填写操作，变成一次进入房间、安顿自己、留下生活痕迹的过程。

项目围绕三个相互关联的使用场景展开：用记录模式承接实际生活，用展开模式观察时间分配，用蓝图功能表达未来意图。在此基础上，进一步加入房间物件交互、桌面陪伴窗口以及未完成事项的收藏空间。

本阶段已形成八类房间资产、可交互的建筑原型与多轮视觉优化成果。开发过程中没有把技术复杂度直接等同于效果：学习房 Diffuse 烘焙、用餐房 AO 烘焙均经过独立测试，因视觉收益不足而未推广；最终采用更可控的实时灯光与墙面局部明度渐变，并解决放大房间的镜头冲突及天花板明暗闪动。

MEELO 的核心价值是一个设计立场：**时间记录可以帮助人看见生活，而不只是检查自己。**“缓解时间焦虑”是项目的设计目标，当前尚未通过正式用户研究证明其实际改善幅度。

## 二、问题意识：当时间只剩下数字

### 2.1 我们记录得越来越细，却未必更理解自己

计时器、待办清单和统计图表能够有效组织任务，但在强调产出与完成率的使用情境中，部分用户也可能产生新的压力：休息需要被解释，计划落空像一次失分，没有显著成果的一天似乎就不值得记录。

MEELO 的设计切入点不是否定效率工具，而是补充它们较少表达的部分：生活的情境、身体的需要、一天之中的情绪与节奏，以及那些没有按计划发生的事情。

本项目以此提出三个设计问题：

1. 能否让用户直观看见“时间去了哪里”，同时保留活动本身的温度？
2. 能否让工作、睡眠、吃饭、社交与娱乐都拥有同等的存在感？
3. 能否让计划服务于生活，而不是让生活不断接受计划的审判？

以上问题来自项目的设计观察与初始假设，并非已完成的访谈或问卷研究结论。

### 2.2 设计目标

| 目标 | 对应设计 | 希望带来的体验 |
|---|---|---|
| 看见时间 | 将活动与时长转化为楼层与建筑高度 | 把抽象数字变成可以观察的空间 |
| 接纳生活的多样性 | 八类活动拥有独立房间 | 休息与日常照料也值得被记录 |
| 降低记录的冷感 | 小猫、家具互动与建造动画 | 从“填表”转向“进入自己的生活” |
| 保留计划的弹性 | 将未来蓝图与实际记录区分 | 看见意图与现实之间的差异 |
| 为未完成留位置 | 脚手架、未完成楼层与收藏入口 | 让中断有一个可回看、可整理的去处 |

## 三、核心概念：让时间成为可以居住的空间

### 3.1 为什么是一栋楼

建筑天然具有积累、结构与归属感。一层层向上生长的楼，既可以表现时间的连续，也允许不同活动并存。用户不需要先读懂复杂图表，就能通过房间颜色、家具和楼层位置辨认自己的生活片段。

项目形成了三个尺度的观看方式：

- **整栋楼：** 观察一天的整体节奏与活动构成。
- **单个房间：** 回到一项活动的具体情境。
- **展开后的建筑：** 用高度重新理解各项活动占用的时间。

这使“记录—体验—回顾”不必依赖彼此割裂的界面，而可以在同一座建筑中完成。

### 3.2 为什么是一只小猫

小猫不是独立于功能之外的装饰，而是用户在三维空间中的行为代理。它乘坐电梯、进入房间、停留和互动，把抽象的计时状态转译为容易理解的动作。

同时，小猫为产品引入了陪伴感：用户面对的是一个正在生活的小小角色，而不只是不断变化的数字。项目希望借此建立更柔和的记录关系；这种情感效果仍需要后续用户测试验证。

## 四、产品系统：记录、展开与蓝图

### 4.1 记录模式：给已经发生的生活一个房间

用户选择活动类型并开始计时，系统根据类别生成相应楼层。当前原型提供正计时、倒计时与番茄钟相关入口，房间则承载活动的视觉情境。

点击楼层后，镜头从整栋建筑进入放大的房间。用户可以与部分家具互动，例如打开冰箱、掀起锅盖、操作水龙头、拉动窗帘或切换灯光。这些细节让一个房间不仅能够“被看见”，也能够“被使用”。

### 4.2 展开模式：用空间比例理解时间

标准模式为不同活动提供一致的楼层尺度；展开模式根据时长调整楼层高度，并设置高度上下限。家具保留在地面附近，天花板与悬挂资产随顶部移动，中间空间用于信息呈现与装饰。

这一设计把“用了多久”转换为直观的建筑差异。但展开高度并不是严格的时间比例尺：最小、最大层高会压缩极短或极长活动的差异，因此仍需要结合时长文字阅读。

### 4.3 蓝图功能：为未来保留一个尚未揭开的空间

蓝图房间通过玻璃覆盖与工程式文字表达计划状态。计划先以可见的建筑形式存在，用户可以查看并手动揭开玻璃。

需要区分原始构想与当前实现：策划案设想计划能够在下一天解锁并衔接实际活动；当前原型已具备蓝图生成、文字显示和揭开交互，但**不能将其描述为已经完成自动跨日转化与计划—实际闭环**。

### 4.4 未完成，也可以被安放

项目在初始策划的基础上发展出未完成楼层、脚手架表现与地下收藏空间。中断不再只对应一个消失的任务，而可以成为建筑中留有痕迹的状态。

这一设计为产品带来更有讨论价值的方向：时间管理是否只能奖励完成，还是也可以帮助用户理解中断？MEELO 希望让未完成的事情能够被看见、被收纳、被重新整理。

“烂尾楼”的表达带有轻松、自嘲的意味，但也可能让部分用户产生负面联想。后续需要测试它究竟更接近接纳，还是会加重挫败感，不能仅凭设计意图断言用户一定感到被安慰。

## 五、视觉语言与关键资产迭代

### 5.1 从场景拼装走向统一的微缩世界

项目采用固定正面剖面视角，以微缩建筑与 Dollhouse 的观看方式组织空间，并保留 Voxel / Low-poly 的简洁造型语言。主预览结合圆润家具、主题配色和像素风界面，形成“三维生活空间＋像素化陪伴”的视觉组合。

房间标准外尺寸在策划中设定为约 **8 × 3.6 × 4.4 m**，墙厚约 **0.12 m**。统一尺度为垂直堆叠、镜头切换和楼层展开提供基础，也让不同房间能够共享建筑结构。

### 5.2 八类房间不是八张皮肤

| 房间 | 典型生活内容 | 核心视觉识别 |
|---|---|---|
| 学习 / 工作 | 阅读、学习与专注任务 | 工作台、书架及学习用品 |
| 睡觉 | 睡眠与睡前休息 | 床、窗帘、柔和灯具与紫色氛围 |
| 用餐 | 做饭、吃饭与补充能量 | 餐桌、厨房台面、冰箱及暖色墙地 |
| 居家 | 家务、整理与居家照料 | 座椅、清洁及洗衣相关物件 |
| 通勤 | 出行与移动 | 与交通及旅途相关的场景陈设 |
| 户外 | 自然接触与户外活动 | 植物、帐篷、野餐与露营物件 |
| 社交 | 交流、相聚与聚会 | 聚会陈设、音响及氛围灯 |
| 娱乐 | 游戏、影音与个人消遣 | 娱乐设备、座椅与屏幕 |

八种场景通过家具、颜色和互动共同表达活动，而不是只替换一个图标。这也使用户能够在整楼视角下迅速辨认活动构成。

### 5.3 家具版本核对与造型统一

迭代中曾出现不同电脑预览到不同家具版本的问题。排查重点从“继续调灯光”转向“先确认正在使用哪一套资产”：核对 Blender 工作文件、导出模型和网页实际加载版本，确认主预览使用已经替换过的圆润家具。

这一步带来的经验是：视觉问题不一定来自渲染参数，也可能来自资产版本不一致。只有模型版本一致，后续材质与灯光对比才有意义。

### 5.4 CMF：让颜色主要由材质承担

用餐房是材质迭代的重点案例。墙面与地面经过多轮颜色比较，最终采用 **#D98C82** 作为基础色。相关材质保持非金属、哑光、不透明，并保留原有微弱自发光设定。

项目逐渐明确了材质与照明的分工：材质承担房间的主题色，灯光塑造亮度、体积和气氛。避免用过强的彩色灯照替代材质配色，从而让房间在不同视角下保持较稳定的色彩识别。

需要注意，材质 HEX 不是最终屏幕颜色。灯光、曝光、色调映射和显示设备都会改变观看结果，因此不能只用色卡判断实际房间是否达标。

## 六、关键技术选择：为什么没有直接采用烘焙结果

### 6.1 先整理资产，再验证效果

项目曾尝试将 Blender 光照烘焙接入网页。准备工作采用非破坏式流程，在独立副本中进行审计、材质隔离与 UV 重建，没有直接覆盖原始模型和旧贴图。

本轮 Blender 资产审计记录了 **3,403 个 Mesh**，发现 **28 组跨房间共享材质**，并在复制后的材质中隔离 **191 个旧 Lightmap 贴图节点**。这组数据属于 Blender 工程审计，不等于网页当前同时渲染的对象数量。

八种房间分别准备独立光照 UV，保留原有纹理 UV、对象名称和层级；动态小猫及可移动物件不参与静态烘焙。UV 检查也记录了极小或退化三角形告警，没有把“流程跑通”当作所有资产问题都已消失。

### 6.2 学习房 Diffuse：工程可用，不代表视觉可用

学习房进行了 1024 × 1024 的 Diffuse 测试，包含直接与间接照明，关闭基础色烘焙。测试证明了独立贴图、UV 导出和网页加载链路可以成立，但仍出现噪点、细小边缘及接缝发暗等问题。

此外，Blender 与网页的色彩管理、着色器能力及显示结果存在差异。独立实验资产与主预览家具版本也并非完全一致，因此不能把实验截图直接当作当前主预览的严格前后对比。

最终决定是：保留工程准备成果，停止该视觉方案的推广，不继续对其余七种房间批量烘焙。

### 6.3 用餐房 AO：可测的变化，不等于值得采用的提升

随后，项目复用已经完成的资产准备流程，对用餐房单独进行 AO 接触遮蔽测试。采用 1024 × 1024 贴图、256 样本、8 px 扩边与约 0.25 m 遮蔽距离，并保持相机、曝光、灯光和基础材质一致。

测试结果表明，AO 贴图生成与网页绑定成功，但视觉改善很轻微：在该实验固定条件下，AO 强度为 0.5 时，全画面显示像素通道均值下降约 **0.0356%**，房间内部区域约 **0.0849%**。这些数字描述的是显示像素变化，不是画质提升百分比。

原因在于，Three.js 的 AO 主要影响间接照明项，对直接灯光和真正的自发光不直接起作用。当画面主要由直接照明构成时，只加 AO 并不能明显重塑家具的体积关系。

这一轮没有获得值得推广的视觉收益，因此同样没有应用到主预览。

### 6.4 从“增加技术”转向“解决画面”

两次实验使项目明确了一个更有效的判断标准：不以技术路线是否复杂为成果，而以用户能否直接感受到清晰、干净、稳定的视觉变化为依据。

资产审计、UV 与材质隔离并没有被废弃，它们保留为后续工作的基础；但当前主预览没有接入这两轮实验的 Diffuse 或 AO 结果。

## 七、最终视觉策略：清楚、柔和、有空间层次

### 7.1 把房间照成微缩空间，而不是一张平面插画

最终优化以主预览现有模型与材质为基准，采用实时灯光与局部材质扩展：

- 从顶部偏后方引入暖白主光，突出家具顶面与后墙上部。
- 降低均匀环境照明与过强的正面补光，让物体保留侧面与正面的明暗差异。
- 保留弱正面照明，避免小猫、柜体和家具正面陷入难以辨认的暗部。
- 仅为墙面加入连续的高度明度渐变，让上部更明亮、下部适当收暗。
- 复用可投影的实时聚光与现有软阴影能力，不把 RectAreaLight 误当作能够直接投射常规阴影的灯型。

墙面渐变作用于三维材质本身，而不是在整个画面上覆盖一张半透明渐变图，因此不会一并压暗家具、屏幕与灯管。

### 7.2 先局部验证，再推广到八种房间

项目先为用餐房建立独立 A/B 页面，再验证睡觉房。比较保持相机与曝光一致，以便判断变化来自灯光和局部墙面控制，而不是取景或整体曝光。

用餐房初版曾出现“空间层次改善，但房间突然变亮”的反馈。随后将整楼视角顶部聚光从 6 降至 2.5，宽面光从 3.8 降至 3.1，保留墙面渐变。这说明优化目标并非让房间更亮，而是在合适亮度下让层次更清楚。

睡觉房采用更克制的参数，保留紫色主题与柔和装饰灯。最后将同一方法应用到八种房间，并分别适配强度，未把用餐房的数值机械复制到所有场景。确认后移除临时 A/B 控件，合入主预览。

### 7.3 保留真实的技术边界

部分主模型家具原本使用固定光照贴图与 MeshBasicMaterial，对新增实时灯光的响应有限。本阶段保留这些既有材质，没有为了制造更大的对比而擅自替换家具表现。

因此，本轮最明确的改善集中在墙面层次、整体空间照明和实时投影，而不是所有家具都已完成统一的物理材质重建。

## 八、交互细节：让陪伴感落在具体操作中

情感化体验需要通过使用细节成立。项目围绕可读性、操作范围和陪伴窗口进行了多项修正：

| 迭代项 | 处理方式 | 设计意义 |
|---|---|---|
| 活动选择面板过高 | 压缩八个按钮高度，保留小猫与单行文字 | 减少面板占用，保持类别可识别 |
| “学习 / 工作”换成两行 | 改为单行，溢出时左右滚动 | 在统一按钮尺度中保留完整名称 |
| 语音入口文案 | 调整为“语音输入自动识别” | 让入口直接说明用途；识别能力依赖浏览器支持 |
| 侧栏标签一直显示 | 保留图标及悬停反馈，文字在 hover 时出现 | 减少常驻界面负担 |
| 地下室难以点击 | 扩大到整个房间开口 | 让可见空间与可点击范围一致 |
| 蓝图文字受灯光影响 | 调整玻璃文字的材质与对比关系 | 提高不同光照条件下的可读性 |
| 房间缩小后选错内容 | 保留当前房间选择，并使用房间专用布局 | 让陪伴窗口承接刚才的活动情境 |

## 九、稳定性修复：从“看起来正常”到连续渲染验证

### 9.1 进入房间时的镜头冲突

快速退出后再次进入房间时，旧退出动画曾继续控制镜头，造成房间反向缩小、随后又放大的异常表现。修复后，新进入操作会清除旧退出动画，并从当前相机位置、朝向和视角接续过渡。

同时，将进房过程中的屏幕空间 AO 改为连续渐入，过渡期间逐帧刷新阴影，减少突然出现的暗部与延迟投影。

### 9.2 天花板持续闪动的独立排查

镜头问题修复后，放大房间的天花板仍会间歇性变暗。项目没有简单将其归结为同一个问题，而是继续在静止机位下采样。

排查发现，同一盏环境补光被两套逻辑以不同强度反复覆盖：一套按帧更新，另一套随天空状态更新。用餐房测试中，其强度曾在 0.36 与 0.195 之间交替，对应天花板同一像素的红通道在 139 与 132 之间变化。

最终将补光强度统一由一个更新位置计算。修复后，用餐房连续 40 帧、睡觉房连续 30 帧的同一点像素采样保持稳定。该结果验证了本次已复现问题的修复，不代表所有设备上的长期兼容性已经完成测试。

> **【图片待补 14｜问题定位与修复证据】**  
> 插入内容：修复前后各一组连续帧，或以帧序号为横轴、天花板采样亮度为纵轴的对比曲线。  
> 数据来源：`work-eight-room-lighting/ceiling-light-trace.json`、`ceiling-after.json`、`sleep-ceiling-after.json`。  
> 建议图注：**从偶发观感到可复现数据：统一补光更新后，天花板不再周期性跳变。**  
> 补图提醒：单张截图不能证明“不闪”，优先使用连续帧或数据曲线。

## 十、技术架构与阶段成果

### 10.1 从原始技术设想到当前实现

初稿提出 React、Vite、React Three Fiber 与 Drei 等技术选择。当前主预览实际采用 **HTML / CSS / JavaScript 与 Three.js 的直接实现**，通过房间配置和模型资产组织场景，并使用本地存储保存原型数据。报告以实际工程为准，不把初稿中的技术设想写成已经采用的架构。

当前资产流程以 Blender 工作为基础，通过 GLB 等格式导出。网页模型以包含 base64 GLB 的 `.txt` 文件组织，配合房间灯光配置加载；它们不是普通文本几何模型。八类房间均为预制资产，不依赖大模型 API 在使用时实时生成。

### 10.2 功能与成果状态

| 模块 | 当前阶段成果 | 仍需推进的部分 |
|---|---|---|
| 建筑与房间 | 八类房间、楼层堆叠、整楼与近景切换 | 更广泛的设备性能与长建筑压力测试 |
| 时间记录 | 活动选择、计时相关入口、记录与楼层表现 | 完整异常场景与长时间使用测试 |
| 展开模式 | 根据时长调整楼层高度及相关资产位置 | 高度映射的信息准确性与可读性测试 |

## 十一、项目价值与设计反思

### 11.1 时间可视化，也可以是一种生活叙事

MEELO 将记录从数字转换为空间，使不同活动不只是统计分类，也成为可以回到其中的生活场景。这种表达保留了时间工具的信息功能，同时为回顾提供了更具体的记忆线索。

### 11.2 游戏化不必只奖励更高的完成率

建造、电梯和小猫为记录提供了即时反馈，但项目不希望把生活变成另一张绩效表。睡觉、吃饭与娱乐拥有自己的房间；未完成事项也有独立的表达方式。它们共同支持一种更包容的日常叙事。

这仍然是一项需要被检验的设计选择：建筑高度是否会引发新的攀比，未完成楼层是否会造成新的压力，小猫是否会从陪伴变为干扰，都应通过真实使用反馈判断。

### 11.3 技术验证必须服从体验目标

两次没有被采用的烘焙实验，构成了项目的重要过程成果。它们帮助项目识别资产与显示链路的边界，并将精力转向更直接的视觉问题，而不是为了证明某种技术路线而继续增加复杂度。

### 11.4 稳定性也是情感化设计的一部分

柔和配色、小猫和微缩场景能够建立第一印象，但持续闪动、错误窗口或突兀镜头会直接破坏安心感。项目将这些问题纳入设计迭代，而非仅视为后期技术修补。对一款希望减少时间压力的工具来说，稳定、可预测和少打断同样重要。

## 十二、后续计划

下一阶段的重点是验证 MEELO 是否真正支持了它希望创造的体验，而不只是让画面更完整。

1. **开展短期使用测试。** 观察用户是否愿意持续记录，休息与未完成是否能够被更自然地接受。结合访谈与自我报告，比较使用前后的感受；在没有数据前，不给出焦虑改善百分比。
2. **补齐计划与实际的衔接。** 明确蓝图揭开、活动开始、实际完成与跨日归档之间的关系，避免视觉暗示超过真实功能。
3. **控制陪伴的打扰程度。** 验证小窗尺寸、悬停信息、互动频率与桌面占用，允许用户自由收起陪伴界面。
4. **统一资产与性能基线。** 继续规范模型版本、材质、命名和导出；针对不同显卡、浏览器与长建筑进行性能检查。
5. **逐步完善数据与历史回顾。** 优先保证本地数据安全和可恢复，再考虑账号、跨设备同步与更长周期的时间建筑。

初稿中的社区、城市与好友建筑可以作为远期探索，但应建立在个人记录体验已经可靠、有价值的基础上。

> **MEELO 希望留下的，不是一张证明自己足够努力的成绩单，而是一座能够告诉自己“今天也认真生活过”的小楼。**
